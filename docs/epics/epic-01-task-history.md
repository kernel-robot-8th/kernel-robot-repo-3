# 에픽 1: 작업·단계 이력

## 목표

작업 생성 이후의 표준 단계와 상태 변경을 저장하고 조회할 수 있게 합니다. 작업 상세 API와 간단한 타임라인 화면을 제공하되, 이 에픽에서는 작업 실행을 시작하지 않습니다.

## 범위

- 작업/단계 데이터 계약과 표준 단계 순서
- 기존 SQLite 데이터 보존을 포함한 스키마 마이그레이션
- 작업 상세 API와 트랜잭션 기반 상태 전이
- 작업 생성·목록 및 상세 타임라인 UI

실제 로봇 명령, 시작 버튼, mock 작업 진행 흐름은 [에픽 2](epic-02-mock-happy-path.md) 이후 범위입니다.

## 데이터 계약

기본 작업은 아래 단계를 이 순서대로 생성합니다. 실행 계획상 단계가 아직 수행되지 않았으면 상태는 `PENDING`입니다. 실제 이동 단계 성공은 Nav2 action의 terminal success로 판정하며 goal 수락, feedback 완료율, lifecycle 상태만으로 성공 처리하지 않습니다.

1. `VALIDATE_ROBOTS`
2. `NAVIGATE_TO_DESTINATION`
3. `VERIFY_ARRIVAL`
4. `EXECUTE_ARM_TASK`
5. `VERIFY_ARM_RESULT`
6. `FINALIZE_TASK`

새 task의 단계 ID는 task 안에서 안정적으로 참조할 수 있어야 하고 순서는 `sequence`로 보존합니다. 기존 DB의 task 행은 유지하되 과거 단계나 이벤트는 추정해 만들지 않습니다. 기존 작업의 상세 조회는 빈 단계·이벤트 목록을 반환합니다.

첫 저장 slice에서는 기존 `Task` 응답 필드를 유지하며 `steps` 배열을 추가합니다. 생성 이벤트는 `TASK_CREATED`로 기록하고, 이벤트 시간은 서버가 생성한 `occurred_at` 및 `received_at`으로 동일하게 시작합니다. 장치 이벤트가 도입되면 두 시각을 분리해 기록합니다.

## 작업 순서와 확인 지점

### 1. 데이터 계약 고정

- [x] `Task`의 생성·실행·완료 필드를 [시스템 명세](../spec/system-spec.md)와 대조
- [x] 위 표준 단계의 이름과 순서를 고정
- [x] 작업 시작 전 이동 로봇 readiness 조건과 이동 단계의 terminal success 의미를 명세에 맞춰 확인
- [x] 장비 입력 형식이 정해지기 전까지 `destination`, `arm_job`을 문자열로 저장
- [x] 이벤트에서 장치 발생 시각(`occurred_at`)과 서버 수신/기록 시각(`received_at`) 구분

**확인 완료:** 명세와 대조했고 이번 첫 구현 slice에서 쓸 저장 계약을 위에 고정했습니다.

### 2. ORM 저장소, SQLite 마이그레이션 및 생성 응답

- [x] SQLAlchemy ORM 모델과 Alembic revision 기반 버전 관리 경로 추가
- [x] 기존 `tasks` 행을 유지하며 `started_at`, `finished_at`, `active_step_id`, 오류 필드 추가
- [x] `task_steps` 테이블 추가: 단계 ID, 작업 ID, 순서, 유형, 로봇 ID, 상태, 명령 ID, 시작·종료 시각, 결과·오류
- [x] `task_events` 테이블 추가: 이벤트 ID, 작업·단계 ID, 종류, 이전·새 상태, 발생·기록 시각, payload
- [x] 새 작업 행, 표준 단계, 생성 이벤트를 한 트랜잭션으로 삽입
- [x] 기존 작업은 행을 보존하고 과거 단계·이벤트를 만들어 내지 않음
- [x] 생성 API 응답에 저장된 표준 단계와 생성 이벤트를 포함해 첫 slice를 바로 확인 가능하게 함

**확인:** 기존 DB의 작업 목록은 요약 형태로 그대로 보입니다. 새 작업 생성 응답에는 순서가 있는 표준 단계와 생성 이벤트가 나타납니다. 기존 작업은 상세 API가 추가되면 빈 이력으로 반환합니다.

### 3. 작업 상세 API

- [x] `GET /api/tasks/{task_id}` 추가
- [x] 단계를 `sequence` 순서로, 이벤트를 서버 기록 순서로 반환
- [x] 기존 `GET /api/tasks`는 요약 목록으로 유지
- [x] 없는 ID는 `404`; JSON 응답의 결과·오류 필드 형태를 일관되게 유지

**구현:** 상세 URL은 `{ "task": { ... } }` 형태로 작업 요약, 단계, 이벤트를 반환합니다. 단계는 `sequence`, 이벤트는 `received_at`과 ID 순서로 반환합니다. 없는 작업 ID와 잘못된 상세 경로는 `404`입니다.

**확인:** 상세 URL에서 작업의 단계와 이벤트를 확인하고 존재하지 않는 ID의 `404` 응답을 봅니다.

### 4. 상태 전이 서비스

- [x] 작업 및 단계 상태별 허용 전이를 명세에 맞춰 구현
- [x] 상태 갱신과 이벤트 삽입을 같은 SQLite 트랜잭션에서 처리
- [x] 이전 상태가 맞지 않는 변경과 금지된 역방향 전이는 거부
- [x] `UNKNOWN`과 `TIMED_OUT`을 성공·실패로 임의 치환하지 않음
- [ ] 장치 이벤트 중복 수신 시 `event_id` 기반 중복 제거

**구현:** 저장소 서비스가 작업·단계 상태를 조건부 갱신하고 상태 변경 이벤트를 같은 트랜잭션에 기록합니다. `expected_status`가 현재 값과 다르거나 동시 갱신이 감지되면 충돌로 처리합니다. `NEEDS_INTERVENTION → RUNNING` 재개에는 운영자 확인 플래그가 필요합니다. 이 서비스는 아직 실행 API나 장치 이벤트 수신기에 연결되지 않았습니다.

**확인:** 허용된 변경은 현재 상태와 이력에 함께 나타나고, 거부된 변경에서는 양쪽 모두 바뀌지 않는지 확인합니다.

### 5. 작업 생성·목록 화면

- [x] 목적지와 팔 작업 입력으로 `POST /api/tasks` 호출
- [x] 최근 작업 목록에 ID, 목적지, 상태 표시
- [x] 빈 목록과 입력 검증 오류를 구분해 표시

**구현:** 작업 이력 영역에서 작업을 등록하고 목록에서 상태를 확인합니다. 화면은 등록 결과와 API 오류를 구분합니다.

**확인:** 화면에서 작업을 만들면 목록에 `PENDING`으로 나타나고, 새로고침 뒤에도 유지됩니다.

### 6. 작업 상세 타임라인

- [x] 목록 항목 선택 시 상세 API 호출
- [x] 단계 순서, 단계 상태, 이벤트 시각을 간단한 이력 목록으로 표시
- [x] 선택 전, 로딩 중, 선택한 작업 없음, API 오류 상태를 구분
- [x] 실행 시작 버튼은 노출하지 않음

**구현:** 선택한 작업의 단계와 이벤트를 같은 화면에서 조회합니다. 실행 시작 버튼은 제공하지 않습니다.

**완료 조건:** 작업을 생성한 뒤 화면에서 `PENDING` 상태, 표준 단계, 생성 이력을 확인할 수 있습니다.
